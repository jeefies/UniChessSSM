## 0. 总览与修订路线

### 0.1 B0 结论（2026-09-16 回填，详见 stage-a-experiment.md §10）

**链路审计全 PASS**：原生路径 ↔ SSMAdapter ↔ 推理服务器三层对拍 fp32 逐位一致（maxΔ=0.0，`tools/ssm_path_audit.py`）；WDL→Q 合约一致（`Q=wdl[0]−wdl[2]` 行棋方视角，`mcts.py:291`，与训练标签完全对齐，一步杀真值 Q=+1.000）；80 局终止审计 0 超时、0 协议/非法着判负（远程模式 0.63s/步）。

**归因对照（各 32 局）**：A 路 MCTS-400 vs 纯 policy = **+719.7 Elo**（搜索增益巨大）；B 路 MCTS-400 vs 屏蔽 value = **+314.4 Elo**（value 头贡献真实）。

**最终归因**：Stage A 模型相对 champion −880 Elo 是**网络本身棋力不足**，链路无 bug。早前"value 弱 ⇒ 搜索增益≈0"的工作假设被 A 路实验**证伪**。

**统计边界（review 意见，记录在案）**：+719.7 与 +314.4 是**两个不同对照**下的差值，不能加减成各模块的独立贡献，也不宜跨对手串联推算纯 policy 的绝对水平（此前"纯 policy ≈ champion−1600"的串联写法已撤下）；它们仅支持"搜索与 value 对当前网络均有实际作用"这一决策结论。

**工程记录（进风险表）**：held-out 评估进程结束后 dataloader worker 未回收、白占 7GB 显存 2 小时（已清理）；infer server 峰值保留 8.6GB 为缓存分配器历史最大块，非泄露。

## 1. 可选后备 · B1 价值短程适配（默认不启用）

### 1.1 定位：从强制前置降为条件触发的后备

B0 实验已证明当前 value 在搜索中有真实贡献（B 路 +314.4 Elo），"value 无信号 ⇒ 搜索空转"的前提不成立。因此主线（§2）直接从 Stage A checkpoint 进入搜索自对弈闭环——搜索产生的 π′ 与 z 同时是 policy 和 value 的监督来源，没有必要先跑一个明显更弱的纯 policy 生成器（review 意见，采纳）。

B1 保留为后备，**仅在以下触发条件之一成立时启用**（启用须作者确认并记变更）：

1. Gumbel 搜索生成吞吐实测不达标，且 §2.9 的降级手段（n=32/m=8、并发调整、§9 逐节点 cache 优化）用尽后仍不够——用无搜索生成垫数据；
2. 主线运行中观察到 value 的分布适配成为主要瓶颈（例：value 校准在自对弈分布上持续恶化而 policy 正常）——用短程适配专修 value。

同时修正两处原有表述（review 意见）：

- **纯 policy 自对弈并不自动解决标签噪声**：一局多局面共享一个结果的问题在自对弈中依然存在；它改善的是分布适配，不是标签信噪比。
- **policy 损失不是严格的防漂移锚**：模仿 τ=1 采样动作 ≈ 模仿原分布，但模仿低温/argmax 动作会把分布进一步变尖（自蒸馏效应），不能承诺"不漂移"。它应称为**自行为克隆正则**；若启用 B1 且观察到漂移，更明确的锚是对**冻结 Stage A policy 软分布的 KL 约束**，而非加大自 BC 权重。

若启用，§1.2–§1.6 规格适用；验收门禁改为**诊断目标**，不阻塞主线（§1.5）。§1.2 生成器同时适用 §2.3 的生命周期测试（槽位复用清空、权重更新后旧状态失效）。

### 1.2 自对弈生成器（B1 唯一的大件新代码，新建 `tools/ssm_selfplay.py`）

形态：**批量并发对局 + 线性 cache 携带**。每步每局仅 1 次前向（E 编码当前局面 + R.step 一格 + f 三头），比 UCI 适配器的"每节点整局重放"便宜约两个数量级。

| 项 | 规格 |
|---|---|
| 并发局数 | 128–512【锁定初值 256，按显存/CPU 实测调】 |
| cache | 每局独立携带 R 的逐层 `(conv_state, ssm_state)`，对局内线性推进，无分支（一致性由 Stage A 验收 #3 保证：整序列 vs 逐步 softmax 差 <1e-4） |
| 选着（探索）【锁定】 | ply ≤ 20：masked policy 分布温度采样 τ=1.0；ply 21–40：τ=0.3；ply > 40：argmax。**纯 argmax 会使所有对局雷同，探索不是可选项** |
| 重复计数特征 | 沿对局增量维护 occurrence 字典（与 `stateseq/data/sequences.py::_board_key` 同口径），逐步填入 785 维特征的重复位 |
| 终局裁决 | python-chess `is_game_over(claim_draw=True)` 语义：将杀/逼和/50 步/三次重复/子力不足，全部由规则引擎判定 |
| 长度封顶【锁定】 | 300 ply，封顶记和棋；**记录封顶率，>20% 须停下来调查**（正常现象应 <10%） |
| CPU/GPU 分工 | GPU 只做批量前向；合法着 mask、裁决、特征编码在 CPU worker（沿用 Stage A 的 12 进程 Pool + 预取模式） |
| 进程卫生 | 退出前显式 terminate+join 全部 worker、`torch.cuda.empty_cache()`（B0 工程记录教训，见 §1.6 风险表） |
| 产出 | v2.5 分片（见 1.3）+ provenance manifest |

吞吐估算：瓶颈在 CPU 侧合法着生成（Stage A 实测 ~16.6k 局面/s/worker），12 worker 下 30 万局 ≈ 小时级。【实现时实测回填：games/s、data_wait】

## 2. B2 · Gumbel 主循环

### 2.1 循环结构：learner 与 champion 分离

```
learner（连续训练体：权重 + 优化器状态跨代持续，不随换代成败回滚）
   │  每代：从 replay buffer 采样训练（遍历预算见 §2.6）
   ▼
challenger = learner 当前快照 ──► 换代 arena（vs champion，同算法同预算）
   │  得分率 ≥55%（400 局）         │  未晋级
   ▼                               ▼
champion = challenger             champion 不变
（生成/评测 actor 更换）            learner 继续训练，状态不回滚
```

- **learner/champion 分离**【锁定】：训练永远从 learner 当前状态继续（优化器矩保留）；champion 只是生成与评测用的冻结副本。挑战失败不重置任何状态——此前"回到 champion 还是接着 challenger 训"的歧义以此为准（review 意见）。
- **换代 arena 口径**【锁定】：候选与基线使用**同一搜索算法、同一预算**（主线 = Gumbel g=0, n=64）。PUCT-400 时代的 +720/+314 不能迁移为 Gumbel-64 的收益预期；与 B0 数字的连续性通过在首轮对 Stage A 基线**同时**跑 Gumbel-64 与 MCTS-400 两个口径对齐一次（此后只用 Gumbel-64）。旧 46M champion 仅作外部参照。
- 单卡分时：生成窗口与训练窗口**交替**（实现简单、无显存争用）；profiling 显示生成期 GPU 空闲后再改并发。【实现时实测回填：每代生成时长 / 训练时长】
- 规模爬坡：首轮闭环 2k–5k 局（§0.2 阶段②），验证后进入 25k 局/代（阶段③）。

### 2.2 Gumbel 搜索精确规格（理论依据：Danihelka et al., ICLR 2022；已按 review 指出的两处错误修正）

**记号**：policy logits `ℓ(a)`（合法掩码后）、价值标量 `q = pW − pL ∈ [−1,1]`（WDL 三头换算【锁定】，和棋=0；该口径已经 B0 合约核对背书，mcts.py:291 同构）、访问数 `N(a)`。送入 σ 前，q 按**本树本次搜索**的 min-max 统计归一（论文口径；归一化统计限定单次搜索，不跨树复用）。

**根节点（每步一次）**：
1. 对每个合法着采样独立 Gumbel 噪声 `g(a)`，按 `g(a) + ℓ(a)` 取 top-m 候选（无放回 Gumbel-Top-k；`m = min(m₀, 合法着数)`，m₀=16【锁定】）。
2. **顺序减半**分配 n=64 次模拟【锁定 n=64/m=16；吞吐不足时降级 n=32/m=8，记变更】：⌈log₂16⌉=4 轮，每轮 16 次模拟均分给存活候选，每轮末按 `g(a) + ℓ(a) + σ(q̂(a))` 淘汰末位一半（16→8→4→2→1）。边界情形（m=1、合法着数非 2 的幂、预算不整除、合法着数 < m₀）的实现行为必须在单测中钉死（§2.8 A#4）。

**非根节点（确定性，但含访问次数修正）【锁定，对齐 mctx `_prepare_argmax_input`，review 修正①】**：
先算改进策略
$$\pi_{imp}(a) = \mathrm{softmax}\big(\ell(a) + \sigma(\mathrm{completedQ}(a))\big)\qquad(\text{在全部合法着上})$$
再选择
$$a^* = \arg\max_a \Big[\pi_{imp}(a) - \frac{N(a)}{1+\sum_b N(b)}\Big]$$
即"访问频率向 π_imp 对齐"的确定性分配：π_imp 暂时固定时，访问比例会收敛到 π_imp，而不是永远重复选 argmax 那一项（例：π_imp=(0.6,0.4) 时逐渐形成 60:40 的访问比）。**"无 UCB"不等于"不考虑访问次数"。**

**补全 Q 与 σ 变换**【锁定】：

```
completedQ(a) = q(a)            若 N(a) > 0
              = v_mix           否则
v_mix = ( v̂ + Σ_b N(b) · Σ_{a:N(a)>0} π(a)q(a) / (Σ_{a:N(a)>0} π(a) + ε) ) / ( 1 + Σ_b N(b) )
σ(q̂)  = ( c_visit + max_b N(b) ) · c_scale · q̂ ,   c_visit=50, c_scale=0.1
```

**c_scale 变更记录**（2026-09-20，`design-deviations.md` §9）：原定 c_scale=1.0 在 128 固定局面
对照中把 ~0.03 的原始 Q 差放大成 18-logit 打分差，KL(π′‖π)=2.20 反超原始 policy 熵 1.81，
60% 局面目标退化为近乎确定选择；32 局同权重搜索对抗验证 c_scale=0.1 明显更强（65.6% vs
34.4%，0 和棋）。**改为 c_scale=0.1**，此前用 1.0 生成的 `stage_b_gen_fix500` 降级为诊断数据，
不进入短训。

其中 v̂ 为当前节点自身的网络价值，π 为当前节点 policy 概率。**端点保护**（review 意见）：节点尚无访问时 v_mix 退化为 v̂；分母加 ε；全部在 fp32 下计算。Q 归一化方式与缩放系数**只取论文版**，不与 mctx 当前默认值混合复制（两版不完全相同）。

**着法选择**【锁定】：
- 实战走子 = 顺序减半的最终幸存着（训练局中 Gumbel 噪声自然提供探索，**不需要** Dirichlet/温度）。
- **评测/换代 arena：g=0**（关闭噪声纯利用；候选选择退化为按 ℓ 取 top-m，最终选择在**候选集内** argmax——不得表述为全部合法着上的全局 argmax，review 意见）。

**训练目标【锁定，review 修正②：支持集 = 全部合法着】**：

$$\pi'(a) = \mathrm{softmax}\big(\ell(a) + \sigma(\mathrm{completedQ}(a))\big)\qquad(\text{在全部合法着上计算})$$

未抽入候选的合法着经 completedQ = v_mix 获得目标概率（σ(v_mix) 对它们是同一常数，故相对概率仍 ∝ π），仅非法着置零。

正确性不变量（单测必须覆盖，§2.8 A#3）：**若所有合法着的 completedQ 相同，则 π′ = π**（logits 只被平移同一常数）。"只在候选集上归一"不满足该性质——没有获得任何区分信息时也会扭曲策略，已废弃。

**改进保证的边界**（review 意见）：论文的 `E_{a~π′}[q] ≥ E_{a~π}[q]` 以**正确动作价值**为前提（completed-Q 证明还使用对应 v_π）；实际系统用网络估计与混合估计，不能据此断言每个真实棋局都改善真实价值。算法性质在已知真值的 bandit/小树上验证（§2.8 A#2），棋局只做冒烟，不做理论断言。

**价值视角**：节点 q 一律存**该行棋方视角**，跨边取负（零和）；与 WDL 训练口径（行棋方归一）一致，且与 B0 核对的 `Q=wdl[0]−wdl[2]` 合约同构。

### 2.3 树与 R cache：根部快照 + 每次模拟独占工作 cache（v1【锁定】；§9 逐节点方案留作优化路径）

**结构**：

- 每局持有**不可变的实战根快照**（R 逐层 conv+ssm cache，bf16 ≈ 0.44 MiB/局），实战走子后根快照线性推进一次。
- **每次模拟从根快照克隆一份工作 cache**——`Mamba2.step` 原地改写传入状态，根快照与工作 cache 必须隔离，模拟结束工作 cache 即弃；沿选中路径逐步重算 h（路径长 d，通常 ≤10）。"不存逐节点 cache"不等于"可以直接在实战根 cache 上重算"（review 意见）。
- 树节点只存：`x = E(完整 785 维特征)`（bf16 **1 KiB**/节点——原写 0.5 KiB 系勘误；另计先验/N/Q/边等树结构）。**E 是完整输入特征的函数**：共享键必须包含全部输入字段（含半回合计数、全回合数、重复参考位）与模型版本——不得用忽略计数字段的置子哈希共享（review 意见）。R 的路径相关状态仍禁止任何按局面合并（§5.3：R 不记棋盘，h 依赖整路径）。
- 叶子扩展 = 1 次 E + 路径重算 d 次 R.step + 1 次 f。

**生命周期测试（新生成器必须覆盖，review 意见）**：

1. 模拟结束后根快照逐字节不变；
2. 批量槽位复用（一局终局、新局入驻同一槽）时，清空该槽的 R cache、occurrence 字典与棋盘状态；
3. 生成进程在一个代次窗口内只加载一次 champion 权重；任何权重更新后，不得沿用旧权重产生的 cache/树；
4. 并发局间无任何 cache 串扰（抽查两局同前缀分叉后输出独立）。

**成本表述（勘误 + 待验证假设，review 意见）**：路径重算的附加开销是**待实测假设**，不是已证事实——R 占推理参数的 19.25M/21.92M，不是可忽略的边角。按主循环每代 25k 局 × 平均 100 ply × 64 模拟估算 ≈ 1.6×10⁸ 次模拟；若平均路径重算 5 次 R.step，约 8×10⁸ 次逐局面步进调用——这是按假设计算的工作量，不是耗时预测。生成器必须记录：实战 ply/s、平均路径深度、R 重算时间占比、GPU 批量大小（§4 回填）。

**降级条款**：profiling 显示 R.step 重算占生成时间 >30% → 切换 §9 逐节点 cache（0.47 MiB/节点 bf16：12 层 × (conv 1024×4 + ssm 16×64×16) × 2B，64 模拟树 ≈ 30 MiB/局）。

**跨局拼批**：树内逻辑（选择/淘汰/备份）在 CPU 逐局串行，网络前向（E / R.step / f）把**所有并发局**的请求拼成大批上 GPU——每轮模拟每局一条路径，按步对齐分批。进程模式与进程卫生纪律同 §1.6。

### 2.6 训练配置（`train/stage_b2.py`，改自 stage_a.py）

**数据源与监督范围**（比例 = **来源分别归约损失后的显式权重**，不是样本条数占比——一条 100 ply 序列与一个单局面谜题按位平均会完全扭曲权重，review 意见）：

| 来源 | 来源权重【锁定】 | policy | value | recon/dyn/mlh | 条件 |
|---|---|---|---|---|---|
| 自对弈（Gumbel） | 0.85 | π′ 软 CE（全部合法着目标） | z | 全项 | P99 / RAPID（生成统一） |
| 人类棋谱 | 0.10 | 实际着法 BC | 对局结果 | 全项 | **保留原始条件** |
| 谜题（plumbing 完成前仅评测，见 §2.7） | 0.05 | 解法首着 | 仅强制将杀标记：战术辅助，独立有效位 | recon/dyn 可参与；**mlh 禁用** | P99 / unknown |

**核心损失**：

- **policy（软目标 CE）【数值安全口径锁定，review 意见】**：先对 logits 做合法掩码（非法位置填**有限**大负数如 −3e4，而非 −inf）再 log_softmax；或等价地对目标支持集显式求和 −Σ π′(a)·logp(a)。终局无合法着的行在 policy 损失前剔除。必须新增"含 padding、终局、软目标的前向+反向有限性测试"（§2.8 A#6）——`0 × (−∞) = NaN` 是已核实的 PyTorch 软标签陷阱：整数标签 CE 对 −inf logits 有限，概率标签 CE 为 NaN。
- **value → z**（自对弈/人类）：同 Stage A 代码零改动；谜题战术 value 用**独立有效位与独立校准统计**（§2.7）。
- **recon 0.1 / dyn 0.5 / mlh 0.1**：防坍缩体检延续（谜题不参与 mlh；封顶截断局不参与 mlh，§2.5）。

**序列长度【锁定】**：训练支持**完整 300 ply**——Stage A 的 T_max=200 截断不得静默继承：生成到 300 却训练前 200 会系统性丢失真实尾段，而 value 最有区分力的恰在近终局区域（review 意见）。microbatch 按 T=300 重新实测。若未来采用分块训练，必须携带/重建正确前缀状态，禁止把中盘片段当作从 h_init 开始的新局。

**训练量：数据遍历预算【锁定，取代固定步数，review 定量意见】**：

每代训练步数 = **min( 3 × buffer 局数 ÷ 512, 2000 )**。

- 即主循环初代（25k 局）≈146 步、buffer 满（10 代 250k 局）≈1465 步、封顶 2000；首轮闭环（2k–5k 局）≈12–29 步。
- 理由：固定 2–4k 步在初代相当于把同一 actor 的冻结搜索目标重复拟合 **35–70 遍**，旧冒烟 500 步约 **218 遍**——对陈旧目标的过拟合风险不可接受；用遍历次数控制才是可解释的预算。
- warmup = **min(200, 当代步数 × 10%)**（总步数降到一两百时不得保留 200 步 warmup）；LR 每代 cosine 3e-5 → 3e-6。
- 小数据阶段（buffer < 50k 局）可降低梯度累积，避免"整批更新次数过少"与"凑步数反复拟合"的两难。
- 冒烟（1,000 局）只做**管道连通性与数值有限性验证**（≤3 遍数据，≈6–20 步），不解读学习曲线。

**其余【锁定】**：replay buffer 最近 10 代按代均匀采样；learner/champion 纪律见 §2.1；优化器 AdamW β(0.9,0.999) wd 0.1；bf16 autocast；grad clip 1.0；有效 batch 512 局；checkpoint/原子保存/SIGTERM/进程卫生同 Stage A 与 §1.6。每代以自对弈 held-out val policy CE 选当代表。

### 2.7 谜题侧挂（作者已批准使用引擎验证数据；首轮闭环仅评测，训练混入待 §2.6 来源归约与 §2.8 A#6 数值安全测试通过后开启）

**CSV 语义【锁定，原规格有误，按官方格式修正】**：Lichess 谜题 CSV 的 FEN 是**对手上一着之前**的局面；`Moves[0]` 是对手那着（铺垫着），执行后才得到呈现给解题者的局面；`Moves[1]` 才是解答首着。统一管线：

```
读 FEN → 执行 Moves[0] → 得解题局面 → 标签 = Moves[1]
```

序列口径【锁定】：以**解题局面为 FEN 根**（无前序历史）喂入 R——训练与评测必须同此一种解释，不得各自为政。该口径与 arena 开局库（UCI `position fen`）的实际使用分布一致。

**多解将杀**：mate-in-1 可能存在多个正确将杀着——评测时任何经规则引擎验证的将杀着均计为正确，不得只认 CSV 那一着；训练标签仍用 CSV 解法首着，不额外构造多解标签。

**监督范围【锁定，review 意见】**：

| 谜题信息 | 可用监督 |
|---|---|
| 解题局面 + 合法解答着 | policy（CE 学 Moves[1]） |
| 输入棋盘 | recon |
| 相邻真实棋盘与对应动作（Moves[0] 转移） | dyn |
| 明确强制将杀标记（主题含 mate） | 战术 value 辅助：z = 行棋方胜，**独立有效位、独立校准统计**——"强制胜"与"当前行为策略能否兑现胜局"语义不同，不与对局 z 的校准混合 |
| 解答片段长度 | **禁止**用作 moves-left（"解答还剩 5 ply" ≠ "对局还剩 5 ply"）；非将杀谜题**禁止**标为行棋方胜 |

**战术评测（首轮闭环即启用）**：固定 held-out 谜题集（50k，按难度分层；多解将杀按上述口径判分）。首轮建档基线；主循环每代评估首着 top-1 与 mate-in-1/2 子集准确率——作为**退化报警**（较历史最佳下滑 >2 个百分点 → 人工排查），不作"逐代不降"的硬门禁（review 意见：对弈能力提高不保证每次更新都提高固定谜题指标）。

**权重警戒**：谜题分布偏战术，来源权重 ≤0.10 红线；监控正常局面的 value ECE，防止校准被带偏。

**关键洞察——先手优势掩盖了真实差距**：A 执白时 16W-16L 全是**零和棋**，而 B 执白时 12 场和棋。
两个模型棋力其实非常接近（各执白胜率同为 16/32），差距主要来自**和棋能力/残局技术**：
Gen-2 执白能把均势局面转化成胜利，Gen-3 执白则大量求和。这与"Gen-3 只用 1k 局数据训练 46 步、
严重欠训练"一致——**下一步应加大数据量与训练步数，而非改架构**。

> ⚠️ **该结论的有效样本量只有 16 局**（见下条），方向性参考，不足以做晋级判定。

**23. arena 确定性与对局多样性缺陷（2026-09-23 发现并修复，`365685b`）——重要**：

arena 用 `gumbel_topm(g=0.0)`，噪声恒 0，且 `self.rng` **不参与任何决策** ⇒ **对局（棋谱与结果）
仅是「网络 + 开局 + 执色」的确定性函数，seed 是死代码**。而开局分配是
`n_openings = min(args.pairs, len(OPENINGS)) = min(8, 16) = 8`，`num_pairs = games/2 = 32`
⇒ 32 对挤在 8 个开局上。实测指纹比对证实：**64 局实际只有 16 个不同对局，每个重复 4 次，
组内棋谱逐字节相同、结果完全相同**。统计后果：

| 项 | 表面值 | 实际有效样本 |
|---|---|---|
| 64 局 arena 的得分率标准误 | 按二项 ≈ ±6% | 按 16 个单元 ≈ ±12%（放大一倍） |
| 400 局门禁（旧配置） | 看起来 n=400 | 实际 n=16，**门禁形同虚设** |

这也解释了此前"两次 32 局跑出完全相同的 20W-8L-4D"：不是巧合，而是同一批确定性对局被重放。
连带结论：**上一节 Gen-3 的 59.4%/40.6% 只是 8 个开局的 16 局对决结果**，不能作为晋级依据。

修复（保持 g=0 锁定不变，用开局多样性换取对局多样性）：

- arena 默认从 `data/openings_200.txt` 加载开局，**保留整行不按 ply 截断**——实测按 6 ply
  截断会把 200 个开局折叠成 114 个，等于人为制造重复对局；
- `opening_plan(n_pairs, library, seed)`：库够用（`n_pairs ≤ 库规模`）时用**带种子的排列**
  为每对分配互不相同的开局（同一 seed 可复现＝固定考卷；换 seed 换考卷，各代次考不同卷）；
- `arena.json` 新增 `distinct_games` / `duplicate_rate`，让每次 arena 自证有效样本量，
  库不足时启动即告警；
- `--pairs` 标记废弃（它的本意是 cap 开局数，极易误用；改用 `--openings-file`）；
- `run_gen3_arena.sh` 改为 `--games 400 --openings-file data/openings_200.txt --seed 20260923`；
- 新增 `tests/test_arena_openings.py`（11 项）锁死不变量：对数 ≤ 库规模时开局零重复、
  计划可复现且随 seed 轮换、真实开局库 ≥200 条、非法行跳过、CRLF 兼容。
- 修复过程中还发现 loader 去重写在截断之前，导致未截断行被自己误删（现改为最终形态去重）。

验证：16 局冒烟 `distinct_games=16 / duplicate_rate=0.0`；远端全量 120 项单测仅剩既有
flaky（`test_arena_workers` 的 mp.Queue feeder 竞态，基线同样复现）。

**待办**：Gen-3 的晋级判定需用修复后的配置**重跑 400 局**（`bash run_gen3_arena.sh`，
200 对 × 2 色，预计约 4.5 小时）；此前 64 局结论仅作诊断参考。

**关键结论（对 25k 局/代的影响）**：n_sims=256 下 25k 局需 ~4.8 天；n_sims=64 下需 ~19 小时。
若阶段③ 25k/代要在合理窗口内闭环，需二选一：①生成仍用 64 sims、256 只用于 arena/评测；
②接受多天级的生成窗口。此项待用户决策（已向用户报告实测数）。
