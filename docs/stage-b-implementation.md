## 0. 总览与依赖链

```
B1 价值 bootstrap（policy-only 自对弈 → 训 value）
   产出：在模型自身分布上有区分度、校准良好的 value 头 + B1 checkpoint
   是 B2 的前置：Gumbel 的 σ(q) 依赖有信号的 value，value 盲则搜索空转
        │
        ▼
B2 Gumbel 主循环（Gumbel 搜索自对弈 → π′/z 目标 → 换代门槛）
   产出：逐代提升的 champion checkpoint 序列
```

两个复用事实（B1/B2 便宜的根本原因）：

1. **数据格式复用**：自对弈只存动作序列 + 元信息，训练时多进程重放重建局面——与 Stage A v2 分片同构，训练器 ~90% 复用 `train/stage_a.py`。
2. **训练目标同构**：Stage A 的 value 目标本来就是"对局结果对行棋方归一"，B1/B2 只换数据源与权重，value 损失代码零改动。

条件输入【锁定】：B1/B2 全程 Elo 置 2567.5（P99，标准化 +2.33σ，与 UCI 默认一致），tc_bucket 固定 RAPID=2，color 逐步取值。Elo 条件标定的维护属 Stage B3，不在本文。

## 1. B1 · 价值 bootstrap

### 1.1 目标与定位

修一个双重问题：① Stage A value 标签信噪比低（人类对局一局 ~80 局面共享 1 个结果，value_gain 仅 0.067 nats）；② value 分布错配——对弈时搜索评估的是**模型自己走到的局面**，与人类棋谱分布不同。两者只有一个共同解：在模型自己的分布上、用自己的对局结果训 value。

**B1 不追求 policy 进步**；policy 损失只作防漂移锚（见 1.4）。

### 1.2 自对弈生成器（B1 唯一的大件新代码，新建 `tools/ssm_selfplay.py`）

形态：**批量并发对局 + 线性 cache 携带**。每步每局仅 1 次前向（E 编码当前局面 + R.step 一格 + f 三头），比 UCI 适配器的"每节点整局重放"便宜约两个数量级。

| 项 | 规格 |
|---|---|
| 并发局数 | 128–512【锁定初值 256，按显存/CPU 实测调】 |
| cache | 每局独立携带 R 的逐层 `(conv_state, ssm_state)`，对局内线性推进，无分支（一致性由 Stage A 验收 #3 保证：整序列 vs 逐步 softmax 差 <1e-4） |
| 选着（探索）【锁定】 | ply ≤ 20：masked policy 分布温度采样 τ=1.0；ply 21–40：τ=0.3；ply > 40：argmax。**纯 argmax 会使所有对局雷同，探索不是可选项** |
| 重复计数特征 | 沿对局增量维护 occurrence 字典（与 `stateseq/data/sequences.py::_board_key` 同口径），逐步填入 785 维特征的重复位 |
| 终局裁决 | python-chess `is_game_over(claim_draw=True)` 语义：将杀/逼和/50 步/三次重复/子力不足，全部由规则引擎判定 |
| 长度封顶【锁定】 | 300 ply，封顶记和棋；**记录封顶率，>20% 须停下来调查**（正常现象应 <10%） |
| CPU/GPU 分工 | GPU 只做批量前向；合法着 mask、裁决、特征重放编码在 CPU worker（沿用 Stage A 的 12 进程 Pool + 预取模式） |
| 产出 | v2.5 分片（见 1.3）+ provenance manifest |

吞吐估算：瓶颈在 CPU 侧合法着生成（Stage A 实测 ~16.6k 局面/s/worker），12 worker 下 30 万局 ≈ 小时级。【实现时实测回填：games/s、data_wait】

### 1.3 数据 schema：v2.5 分片（v2 超集）

| 文件 | 布局 |
|---|---|
| `*.meta.bin` | v2 的 16B/局记录 + 追加 16B provenance：u32 gen_id（生成批次号）/ u32 ckpt_step / u32 flags（温度日程版本等）/ u32 pad |
| `*.actions.bin` | 与 v2 相同：uint16 动作 id 池 |

manifest.json 增加 `gen` 节：生成时间、并发参数、温度日程、封顶和棋率、和棋率、平均局长。**人类 Stage A 分片原样保留**，训练按批混入（见 1.4）。

### 1.4 训练配置（`train/stage_b1.py`，改自 stage_a.py）

| 损失 | 权重【锁定】 | 说明 |
|---|---|---|
| value → z（自对弈结果，行棋方归一） | **1.2（主角）** | 代码零改动，换数据源 |
| policy → 走到的着法（自 BC） | **0.2（锚）** | 必须有锚：E/R 是共享主干，"只训 value"是幻觉——value 梯度推主干，policy 无锚会被拖漂 |

| 风险 | 早期信号 | 对策 |

## 2. B2 · Gumbel 主循环

### 2.1 循环结构

```
champion ckpt ──► 生成器（Gumbel 搜索自对弈 N 局/代）
                      │  v3 分片（逐 ply 稀疏 π′ + 结果 z）
                      ▼
              replay buffer（最近 10 代）
                      ▼
              训练（每代 2–4k 步）──► challenger ckpt
                      ▼
              换代 arena（400 局，≥55% 晋级）
                   成功 → challenger 成为新 champion
                   失败 → champion 留任，数据保留，继续训练下代
```

单卡分时：生成窗口与训练窗口**交替**（实现简单、无显存争用）；后续若 profiling 显示生成期 GPU 空闲，再改并发。【实现时实测回填：每代生成时长 / 训练时长】

### 2.2 Gumbel 搜索精确规格（理论依据：Danihelka et al., ICLR 2022）

**记号**：根节点 policy logits `ℓ(a)`（合法掩码后）、价值标量 `q = pW − pL ∈ [−1,1]`（WDL 三头换算【锁定】，和棋=0）、访问数 `N(a)`。

**根节点（每步一次）**：
1. 对每个合法着采样独立 Gumbel 噪声 `g(a)`，按 `g(a) + ℓ(a)` 取 top-m 候选（无放回 Gumbel-Top-k；`m = min(m₀, 合法着数)`，m₀=16【锁定】）。
2. **顺序减半**分配 n=64 次模拟【锁定 n=64/m=16；吞吐不足时降级 n=32/m=8，记变更】：⌈log₂16⌉=4 轮，每轮 16 次模拟均分给存活候选，每轮末按 `g(a) + ℓ(a) + σ(q̂(a))` 淘汰末位一半（16→8→4→2→1）。

**非根节点**：确定性选择 `argmax_a [ ℓ(a) + σ(q̂(a)) ]`（无噪声、无 UCB、无 C_puct 可调）。

**补全 Q 与 σ 变换**【锁定，论文默认】：

```
completedQ(a) = q(a)            若 N(a) > 0
              = v_mix           否则
v_mix = ( v̂ + Σ_b N(b) · Σ_{a:N(a)>0} π(a)q(a) / Σ_{a:N(a)>0} π(a) ) / ( 1 + Σ_b N(b) )
σ(q̂)  = ( c_visit + max_b N(b) ) · c_scale · q̂ ,   c_visit=50, c_scale=1.0
```

其中 v̂ 为当前节点自身的网络价值，π 为当前节点 policy 概率。

**着法选择与训练目标**【锁定】：
- 实战走子 = 顺序减半的最终幸存着（训练局中噪声自然提供探索，**不需要** Dirichlet/温度）。
- 训练目标 `π′ = softmax( ℓ(a) + σ(completedQ(a)) )`（仅 m 个候选上非零，稀疏存储，见 2.5）。
- 论文保证 `E_{a~π′}[q] ≥ E_{a~π}[q]`：有限模拟下的策略改进算子。
- **评测/换代 arena：g=0**（关闭噪声，纯利用；候选选择退化为按 ℓ 取 top-m）。

**价值视角**：节点 q 一律存**该行棋方视角**，跨边取负（零和）；与 WDL 训练口径（行棋方归一）一致。B0 的合约核对结论须在此对齐复核一次。

### 2.3 树与 R cache：v1 采用"根部 cache + 路径重算"【锁定 v1；§9 方案留作优化路径】

**决策**：v1 不在每个树节点存 R cache，改为——每局只存**根节点的 R cache**；每次模拟从根沿选中路径逐步重算 h（路径长 d，通常 ≤10）；每节点只缓存 `x = E(B)`（E 是纯局面函数、与历史无关，按节点存，0.5 KB/节点，可放心按局面哈希共享）；叶子扩展 = 1 次 E + 路径重算 d 次 R.step + 1 次 f。

**理由**：① 正确性优先——消除 copy-on-write cache 克隆这一整类 bug（设计文档 §9 的逐节点方案留作 profiling 后的优化路径）；② R.step 是 12 层 d=512 的小步进，路径重算附加开销小；③ 内存从 ~0.47 MiB/节点 降到 ~0.5 KiB/节点（只存 x + 树结构），并发局数不再受 cache 显存约束。**注意 §5.3 设计事实：R 不记棋盘，h 依赖整路径——禁止按棋盘哈希合并 R 状态，路径重算天然满足此约束。**

**降级条款**：若 profiling 显示 R.step 重算占生成时间 >30%，切换回 §9 的逐节点 cache（0.47 MiB/节点 bf16：12 层 × (conv 1024×4 + ssm 16×64×16) × 2B，64 模拟树 ≈ 30 MiB/局）。

**跨局拼批**：树内逻辑（选择/淘汰/备份）在 CPU 逐局串行，网络前向（E / R.step / f）把**所有并发局**的请求拼成大批上 GPU——每轮模拟每局一条路径，按步对齐分批。与 B1 生成器共用"GPU 前向 + CPU 规则引擎"的进程模式。

### 2.7 谜题侧挂（作者已批准使用引擎验证的谜题数据）

数据源：Lichess 谜题库（CSV：FEN + 解法着法序列 + 主题 + 难度分）。两个用途：

1. **战术门禁（必做）**：固定 held-out 谜题集（50k，按难度分层抽样），每代评估：解法首着 top-1 准确率、mate-in-1/2 子集准确率。**要求逐代不降**（允许 ±0.5% 噪声带），作为当代表选择的辅助判据与退化报警。
2. **训练混入（可选模块，默认开）【锁定初值：开，5%】**：每批 5% 谜题局面，policy CE 学解法首着；mate-in-N 局面给 value 干净标签（有强制胜 ⇒ z=行棋方胜）。
   **口径决策【锁定】**：谜题以 FEN 为序列根（无前序历史），即长度递增的 FEN 根序列喂入 R——与 arena 开局库（UCI `position fen`）的实际使用分布一致，顺带增强 FEN 根鲁棒性。此为与 Stage A 训练分布的已知差异，记录在案。
   **权重警戒**：谜题分布偏战术，混入比例不得超过 10%，防止 value 校准被带偏；监控正常局面的 value ECE。

| 单卡分时效率低 | 交替窗口是保守起点；profiling 后可将训练窗口嵌入生成期 GPU 空闲段 |
