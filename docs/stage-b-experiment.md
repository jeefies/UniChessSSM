## 1. review.txt 四项验证结果

### 1.1 终止原因交叉核对（全部 1,000 局重放）

| 检查项 | 结果 |
|---|---|
| 记录 vs 实际终止不匹配 | **0 局** |
| 300 ply 末尾已将杀 | 1 局（未错记为封顶） |
| 300 ply 末步自然终局 | 4/244 局（正确记录） |
| 实际五十步和棋 | **0 局** |
| 实际三次重复 | **0 局** |
| 封顶局面占比 | **73.3%**（155,400/212,003 ply） |

> **关键发现**：封顶局贡献了约 3/4 的训练位置，且全部贴"和棋"标签。这改变了价值学习的目标分布：value 主要在"人工和棋"局面上训练，而不是自然终局。规格已明确封顶记和是工程约定，但 73% 的比例需要引入阶段②做明确选择：是否保留当前标签，还是调整封顶或价值监督。

### 1.2 重建四格对照（冻结 Stage A, eval mode, dropout=0）

| 检查点 | 人类验证集 | 自对弈验证集 |
|---|---|---|
| **Stage A 冻结** | recon acc **95.9%** / dyn 0.43 | recon acc **62.1%** / dyn 0.52 |
| **5 步冒烟后** | recon acc 90.7% / dyn 0.40 | recon acc 57.2% / dyn 0.49 |

> **分析**：Stage A 在自对弈分布上原本就只有 62.1%（vs 人类 95.9%），5 步训练后掉到 57.2%（-5pp）。**这不是训练退化，而是分布偏移**——自对弈局面的棋局分布、升变模式、子力组合与人类棋谱不同。D 不经过 R 主干（`B → E → D`），序列长度不是原因。C 组门禁的"recon acc ≥ 90%"需要按分布明确化：人类集上的回归检查（95.9%）和自对弈集上的初始化基线（62.1%）。

### 1.3 π′ 目标熵与 CE 分解（200 局, 42,583 ply）

| 指标 | 值 |
|---|---|
| H(π′) 均值 | **0.0605** |
| H(π′) 中位数 | **0.0000** |
| H(π′) P75 / P95 | 0.000 / 0.595 |
| 平均合法着数 | 26.4/ply |
| 概率和最大偏差 | 3.66e-04 |
| ID 重复 | **0/42,583 ply** |

> **意义**：75% 的 π′ 目标是**硬目标**（熵=0）。Gumbel 搜索的 σ(completedQ) 强烈锐化了分布。因此 CE(π′, p) ≈ KL(π′||p)，自对弈 policy CE 4.12 主要反映预测与搜索目标的差距，不能简单归因于"软标签更难"。**soft CE 实质上退化为 hard CE**，并不需要额外的数值安全保护。

### 1.4 ID 集合一致性（200 局全量校验）

| 检查项 | 结果 |
|---|---|
| 实战动作非法 | **0 局** |
| pipol ID 集与合法着集不匹配 | **0/42,583 ply** |
| pipol legal_count 不匹配 | **0/42,583 ply** |

> **最强验证**：π′ 目标的 action ID 集合与规则的合法着集合完全一致。`_resolve_move` 修复后数据完整性无问题。

## 2. Gumbel-64/16 正式配置预检

### 2.1 n_sims=64 vs n_sims=32 对比

| 指标 | n_sims=32/m0=8 | n_sims=64/m0=16 | 变化 |
|---|---|---|---|
| 总局数 | 1,000 | 256 | — |
| games/s | 0.327 | **0.123** | −62% |
| 将杀率 | 33.8% | **39.8%** | +6pp |
| 封顶率 | 51.8% | **50.8%** | −1pp（无显著变化） |
| 逼和率 | 7.0% | 5.5% | −1.5pp |
| 搜索节点/ply | 31.8 | **61.0** | +92% |
| 模拟/ply | 32 | 64 | +100% |

> **核心结论**：**审查的怀疑是正确的**。将模拟从 32 翻倍到 64，封顶率几乎不变（51.8%→50.8%）。问题不在搜索深度，而在**模型本身的终局兑现能力**——即使在 64 次搜索下，模型也找不到足够的杀着。将杀率从 33.8% 提升到 39.8% 说明搜索略有帮助，但不足以让过半棋局在 300 步内结束。

### 2.2 吞吐估算（基于 Gumbel-64 实测）

| 数据量 | 仅生成时间 | 含验证+训练 |
|---|---|---|
| 256 局（验证集） | ~35 min | — |
| 2,000 局（首轮） | ~4.5 h | ~5 h |
| 25,000 局（主循环） | ~56 h | ~58 h |

### 2.3 封顶问题诊断

**五十步/三次重复：0 局**。长局全部由 300 ply 封顶结束，没有规则和棋。这排除了"重复局面绕行导致封顶"的假设。封顶率高是因为：
- 模型**价值头在必胜局面下不够自信**，不主动追求将杀
- 策略头在优势局面下选择"安全"的着法（兑子、简化），而非进攻性的杀着
- 搜索虽有 64 次模拟，但 g=0 评测模式下去除噪声后，根策略的改进有限

**不建议简单提高 cap 到 400**——这会掩盖问题而非解决。如果 300 ply 下封顶率 50%，400 ply 下可能仍>30%。

## 3. 搜索算法实现（`stateseq/gumbel.py`）

### 3.1 基础数值（§2.2【锁定】）

| 超参 | 值 | 说明 |
|---|---|---|
| c_visit | 50.0 | σ 的访问数偏置 |
| c_scale | 1.0 | σ 的价值缩放 |
| EPS | 1e-8 | v_mix 分母保护 |
| NEG_LOGIT | -3e4 | 非法动作有限大负数 |
| N_SIMS | 64 | 根节点顺序减半总预算 |
| M0 | 16 | 根节点候选数上界 |

### 3.2 两处算法规格修正（按 review/mctx）

| 修正 | 原实现 | 现实现 |
|---|---|---|
| ① 非根节点选择 | 固定 `argmax[ℓ + σ(q̂)]`（忽略访问次数） | `argmax[π_imp − N/(1+ΣN)]`——访问频率向 π_imp 收敛 |
| ② π′ 支持集 | 仅在候选集上归一 | **全部合法着**上计算 softmax；未抽入候选的合法者通过 v_mix 获得目标概率 |

### 3.3 递归深化（修复前 vs 修复后）

| 维度 | 修复前（`do_sim`） | 修复后（`_simulate`） |
|---|---|---|
| 树结构 | 固定 root→child→leaf 2 层 | 递归下探，children 持久化 |
| 符号 | 非终局分支少取负一次 | 每层级精确取负（零和） |
| 节点数 | ~2 × 模拟数 | 至多 m₀ × avg_depth |
| 单测覆盖 | `_expand_stub` 全终局 | `_expand_chain` 变深链 + 端到端符号回归 |

## 4. 生成器（`tools/ssm_gumbel_selfplay.py`）

### 4.1 架构

```
run_workers(args) ── subprocess.Popen × N ── Worker ── Driver ── GameState
     │                        │                    │          └ coroutine: yield model requests
     │                        │                    └ _model_step: concat_caches → batch forward → split
     └── _merge_worker_outputs: 搬回分片 + 合并 manifest
```

### 4.2 网格搜索定档（n_sims=32/m0=8, 100 局基准）

| 配置 | games/s | GPU 利用率 | 备注 |
|---|---|---|---|
| 1×16（旧单进程基线） | 0.085 | 17% | GPU 大部分空闲 |
| 10×4 | 0.129 | 95% | 太多小 batch |
| 6×8 | 0.171 | 97% | |
| 5×16 | 0.219 | 99% | |
| **4×24（定档）** | **0.282** | **99%** | 最优 |
| 3×40 | 0.278 | 99% | 与 4×24 平台期 |

**定档原因**：最少进程 × 最大单进程 batch → 最少 CUDA context 争用。超出 4 进程后 GPU context 切换开销吃掉并行增益。

### 4.3 数据完整性修复

**问题**：`action_to_move` 对升后（Queen）返回 `promotion=None`（升后与后走法共用 id 编码，表格中 promo=None）。`board.push` 不自动补旗标——兵走到 8 排后停留在原地。旧生成 504/1,000 局数据损坏。

**修复**：`_resolve_move(a, board)` 在 `board.legal_moves` 中逐 id 匹配，取 python-chess 生成的完整 Move 对象（含 promotion/EP/易位旗标）。

**代码审计结果**：全项目 6 处 `action_to_move` 调用点：
- `ssm_gumbel_selfplay.py`（生成器）：已修复 ✅
- `ssm_path_audit.py:104`（审计工具，不生成训练数据）：未修 ⚠️
- `test_actions.py`, `test_g_alignment.py`, `test_legal_mask.py`：测试代码，使用前校验合法着 ✅

### 5.2 显存实测（T=300）

| microbatch | accum | 有效 batch | 结果 |
|---|---|---|---|
| 32 | 16 | 512 | ❌ OOM（14.05/15.51 GiB） |
| **8** | **64** | **512** | ✅ 通过 |

### 5.3 冒烟训练日志（5 步）

```
step 1/5 loss 17.3971 sp_pol 4.396 sp_val 2.321 human_pol 1.904
VAL:
  human_loss_policy: 2.07, human_loss_value: 0.83, human_recon_acc: 90.7%, human_dyn_rel_err: 0.40
  selfplay_loss_policy: 4.12, selfplay_loss_value: 0.96, selfplay_recon_acc: 57.2%, selfplay_dyn_rel_err: 0.49
```

**关键指标解释**：
- **policy CE 4.12 ≈ KL(π′||p)**：75% 的 π′ 熵为 0，soft CE 退化为 hard CE。4.12 反映模型预测与 Gumbel 搜索目标的差距

- **dyn rel err < 1.0**：防坍缩检通过

## 8. 封顶问题专题分析

### 8.1 事实

| 指标 | n_sims=32 | n_sims=64 |
|---|---|---|
| 封顶率 | 51.8% | 50.8% |
| 封顶局面占比 | 73.3% | ~73% |
| 将杀率 | 33.8% | 39.8% |
| 五十步/三次重复 | 0% | 0% |

### 8.2 假设排除

| 假设 | 证据 | 判定 |
|---|---|---|
| 搜索深度不足，翻倍模拟可改善 | 32→64 封顶率无变化（51.8%→50.8%） | ❌ 排除 |
| 重复局面绕行导致封顶 | 三次重复=0，五十步=0 | ❌ 排除 |
| 搜索实现有 bug（预算不守恒） | budget_check=True, 审计通过 | ❌ 排除 |
| 模型终局价值弱，找不到杀着 | 将杀率仅提升 6pp（32→64） | ⚠️ 最可能根因 |
| 300 ply 不够长 | 需先诊断尾段模式 | ❓ 未验证 |

### 8.3 处理建议

1. **保留封顶记和标签**（工程约定，当前不改）
2. **首轮闭环先用 2k 局**，记录 value 在封顶/自然终局上的区分能力
3. **若训练后封顶率仍 >40%**，考虑：
   - 将封顶局 value 损失权重降至 0.5（减少人工标签影响）
   - 检查封顶局最后 30 ply 的搜索行为（是否为反复绕行）
   - 如必要，cap 可升至 400 但记录决策
