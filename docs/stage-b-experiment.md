## 1. 搜索算法实现

### 1.1 基础数值

| 超参 | 值 | 来源 |
|---|---|---|
| c_visit | 50.0 | §2.2 锁定 |
| c_scale | 1.0 | §2.2 锁定 |
| EPS | 1e-8 | v_mix 分母保护 |
| NEG_LOGIT | -3e4 | 非法动作填充（有限大负数，非 −inf） |
| N_SIMS | 64 | 根节点顺序减半总预算 |
| M0 | 16 | 根节点候选数上界 |

### 1.2 根节点选择流程

```
每步:
1. g(a) ~ Gumbel(0,1) → g(a) + ℓ(a) → top-m0 候选
2. 顺序减半分配 n=64 模拟到 ⌈log₂m₀⌉=4 轮
3. 每轮末按 g(a) + ℓ(a) + σ(q̂(a)) 淘汰末位半数 (16→8→4→2→1)
4. 最终 = 末轮唯一幸存者
```

| 边界条件 | 处理 | 单测 |
|---|---|---|
| m=1（仅 1 合法着） | 全部预算给同一候选 | A#4 |
| 合法着数非 2 的幂 | 末轮保留 1 候选 | A#4 |
| 预算不整除 | 前 rem 个候选多分 1 次 | A#4 |
| 合法着数 < m₀ | m = 合法着数 | A#4 |

### 1.3 非根节点选择（review 修正①）

```
π_imp(a) = softmax(ℓ(a) + σ(completedQ(a)))    全部合法着
a* = argmax[π_imp(a) − N(a) / (1 + ΣN)]
```

修正前：`argmax[ℓ + σ(q̂)]`——忽略访问次数，重复选同一着。
修正后：访问频率向 π_imp 收敛（例：π_imp=(0.6,0.4) → 60:40 访问比）。

### 1.4 补全 Q 与 σ

| 公式 | 说明 |
|---|---|
| completedQ(a) = q(a) if N(a)>0 else v_mix | 已访问：网络 Q；未访问：混合估计 |
| v_mix = (v̂ + ΣN · Σπ(a)q(a) / (Σπ(a) + ε)) / (1 + ΣN) | 端点保护：零访问时退化为 v̂ |
| σ(q̂) = (c_visit + max N(b)) · c_scale · q̂ | c_visit=50, c_scale=1.0 |

### 1.5 训练目标 π′（review 修正②）

```
π'(a) = softmax(ℓ(a) + σ(completedQ(a)))    全部合法着
```

修正前：仅在候选集上归一 → 不满足不变量。
修正后：全部合法着 → 相同 completedQ ⇒ π′ = π。

### 1.6 修复的 Bug

| Bug | 发现 | 影响 | 修复 |
|---|---|---|---|
| 升后/EP 旗标丢失 | 训练冒烟（504/1000 坏局） | 兵停 8 排，棋盘静默损坏 | `_resolve_move(a,board)` 对照 legal_moves |
| Gumbel 回传符号 | 代码审查 | 非终局分支根 Q 反转 | 递归 `_simulate` + children 持久化 |
| 生成器串行 | 实测 0.085 games/s | GPU 利用率 17% | 协程拼批 + 多进程编排 |
| 训练器未接入自对弈 | 代码审查 | π′ 目标从未参与训练 | `policy_soft_loss` + 来源归约 |
| T_MAX=200 静默继承 | 规格检查 | 300 ply 被截头 | 可配置 t_max=300 |
| policy_soft_loss 形状 | 集成测试首跑 | B>1 时广播失败 | `.reshape(-1)` |

## 3. 生成器性能与并发调优

### 3.1 架构

```
run_workers ── subprocess.Popen × N ── Worker ── Driver ── GameState
     │                │                     │         └ 协程 yield model requests
     │                │                     └ _model_step: concat_caches → forward → split
     └── _merge_worker_outputs: 搬分片 + 合并 manifest
```

**关键实现细节**：
- 协程 `GameState.run()` 在每步需要模型前向时 `yield (features, tc, elo, color, cache)`
- `Driver` 攒活 → `concat_caches(list_of_batch1_caches)` → `model.step(features, tc, elo, color, batched_cache)` → `split_cache`
- 每步拼批的逻辑批次大小 ≈ 并发局数（无空闲槽）
- 展开 `_expand_gen` 沿 `node.path` 复制棋盘 + 重算 occurrence，从那步起推 cache 再展开一步

### 3.2 网格搜索定档（n_sims=32/m0=8, 100 局基准）

| 配置 | games/s | GPU 利用率 | GPU 显存 | 特点 |
|---|---|---|---|---|
| 1×16 | 0.085 | 17% | ~1.5 GiB | 基线：GPU 空转，CPU 单核 100% |
| 10×4 | 0.129 | 95%+ | ~4.0 GiB | 太多小 batch，CUDA context 切换频繁 |
| 6×8 | 0.171 | 97%+ | ~4.2 GiB | |
| 5×16 | 0.219 | 99% | ~4.5 GiB | |
| **4×24 ⭐** | **0.282** | **99%** | **~4.7 GiB** | **定档：最少进程×最大单进程 batch** |
| 3×40 | 0.278 | 99% | ~4.9 GiB | 平台期，与 4×24 无异 |

**定档理由**：超出 4 进程后 GPU context 切换开销吃掉并行增益。每进程更大的 batch 提升 GPU kernel 利用率。5×16 就已 99%，4×24 是稳定最优。

### 3.3 Gumbel-32 vs Gumbel-64 吞吐

| 配置 | 局数 | n_sims | games/s | plies/s | nodes/ply | 封顶率 |
|---|---|---|---|---|---|---|

| 首轮训练（gen2k） | 2,000 | 64 | 0.134 | 27.0 | 60.9 | 54.2% |

> n_sims=64 约 n_sims=32 的 2.4× 墙钟（一倍搜索量 + cache 重算路径更长）。
> 每个搜索节点的平均前向成本 ≈ 0.02ms（batch=24, T=1 单步前向）。

## 8. 封顶问题专题

> **⚠️ 8.1–8.4 基于错误数据，已于 2026-09-19 整节作废（commit 784dc64）。**
> §8.2 的核心推理以"五十步=0、三次重复=0"为由排除了「重复/五十步绕行导致封顶」，
> 而这两个 0 恰是终局分类 bug 的产物。真相相反：**三次重复是第二大终局原因
> （gen2k 38.0%）**，"绕行"非但未被排除，还是主导现象；真实封顶率仅 **15.9%**。
> 修正后的事实与结论见 §8.5；以下四小节保留作错误记录，**不得引用**。

### 8.1 基本事实（作废）

| 指标 | n_sims=32 (1,000 局) | n_sims=64 (2,000 局) |
|---|---|---|
| 封顶率 | 51.8% | **54.2%** |
| 将杀率 | 33.8% | 33.2% |
| 逼和率 | 7.0% | 7.2% |
| 子力不足 | 7.4% | 5.4% |
| 五十步/三次重复 | 0/0 | 0/0 |
| 封顶 ply 占比 | 73.3% | **80.7%** |
| 平均局长（自然终局） | ~78 ply | ~77 ply |
| 平均局长（封顶局） | 300 ply | 300 ply |
| 总 ply | 212,003 | 403,094 |

### 8.2 假设检验

| 假设 | 证据 | 判定 |
|---|---|---|
| **搜索深度不够，翻倍可改善** | 32→64：封顶率不变（51.8%→54.2%） | **❌ 排除** |
| **重复/五十步绕行导致封顶** | 五十步=0，三次重复=0 | **❌ 排除** |
| **搜索预算不守恒（实现 bug）** | avg_sims/ply 精确 = 64.0（manifest） | **❌ 排除** |
| **300 ply 不够长** | 未见 300 末步即将将杀或一端明显优势 | **❓ 未验证** |
| **模型终局兑现能力弱** | 将杀率低，封顶局末尾无杀着尝试 | **⚠️ 最可能根因** |

### 8.3 封顶标签对训练的影响

- **80.7% 的训练 ply 来自人工和棋标签**（300 ply 截断 = 和棋）
- Value 主要在"300 ply 未分胜负 = 和棋"上训练
- 封顶标签是**工程约定**，不是 bug——但约 73–81% position 的 value 监督来自"人工和棋"
- **mlh 损失已正确剔除封顶局**（`mlh_valid_mask`），但 value 仍参与

### 8.4 建议

| 方向 | 说明 | 优先级 |
|---|---|---|
| 保留封顶记和标签，推进多代 | 当前约定不改，先看训练能否改善封顶率 | **推荐** |
| 封顶局 value 降权（0.5） | 减少人工标签对 value 的影响 | 低 |
| 调查封顶局末 30 ply 尾段 | 分析是否为反复绕行/漏杀 | 中 |
| cap 升至 400 | 但在封顶根因解决前只会推迟问题 | 低 |

### 8.5 修正后的事实与结论（2026-09-19）

| 指标 | 验证集 256 局 | **首轮 2,000 局** | Round 2 2,500 局 |
|---|---|---|---|
| 将杀率 | 39.8% | **33.2%** | 34.3% |
| **三次重复** | **39.5%** | **38.0%** | **35.9%** |
| 逼和率 | 5.5% | **7.2%** | 7.0% |
| 子力不足 | 3.9% | **5.4%** | 5.6% |
| 五十步 | 0 | **0.3%** | 0.3% |
| **真实封顶率（局级）** | **11.3%** | **15.9%** | **16.8%** |
| **真实封顶率（位置级 ply）** | **17.6%** | **23.7%** | **25.2%** |

> 位置级占比高于局级（截断局偏长，每局贡献满 300 ply），但与此前记录的 **80.7%** 完全不同。
> 两个口径都应记录：训练看到的是位置，数据健康门槛（§1.2 的 20% 调查线）按局级计。

修正后的判断：

1. **"封顶危机"大部分是记账错误。** 真实封顶率 11–17%，略高于 §1.2 的 <10% 期望，
   但不构成管道异常，不触发">20% 须停下来调查"的条款。
2. **真正的现象是"重复和"**：约 36–40% 的对局以三次重复告终。旧 §8.2 对
   「重复/五十步绕行」的排除因此不成立。
   > **但"重复和多 ⇒ 终局兑现能力弱"目前只是假设，未被证实。** 三次重复只描述**结束方式**，
   > 不说明进入重复前是哪一方占优、是否存在可兑现的胜势：均势下主动求和、劣势下成功逼和、
   > 优势下错失胜机，都会产生三次重复。要确认需补充"进入重复前若干 ply 的评估分布 +
   > 子力/局面优势"分析。**在此之前不据此修改和棋奖励或搜索目标。**
3. **训练标签影响大幅缓解**：来自"人工和棋"的 value 监督从约 73–81% 的 ply 降到实际封顶
   局对应的比例；且三次重复是**规则真和棋**，其 z=和是真值而非工程约定。
   `mlh_valid_mask` 的有效局从 46% 回升到 84%。
4. **§8.4 建议相应调整**：「封顶局 value 降权」的动机已基本消失（封顶局占比小且标签多为真和）；
   「调查封顶局末 30 ply」应改为**调查重复和对局的中残局兑现**；「cap 升至 400」继续搁置。

原因是逐节点归一化把分母从全树量程换成了本节点量程（常常只有 ~0.2），
而 σ 展幅 = (c_visit + maxN)·c_scale·1.0 ≥ 51，远压过 ℓ 的量级。
**后果：soft CE 事实上退化为 hard CE**，§4.3 修正后的结论（"soft CE 不可退化"）
对**新数据**不再成立——软目标带来的信息量基本丢失。

#### 归因未分离（记录在案）

新旧两批之间同时变了**两组**东西：adapter 修复与 Q 归一化定义。
按 σ 与 ℓ 的量级推导，**熵坍缩几乎可以确定来自逐节点归一化**；
而将杀率提升更可能来自 adapter 修复（终局真值 + 校准后的 q）。
**但本批数据不能证明这一拆分。** 要分离需一次消融：保持 adapter 修复、
仅将归一化切回全树量程，生成同规模小批对照。

#### 未动的超参

按既定纪律，本轮**不调整 `c_scale`**，也不因熵坍缩回退归一化定义——
先记录现象。`c_scale` 是与归一化定义**不同**的一个变量，若要压低 σ 展幅
（例如 `c_scale` 由 1.0 降至 ~0.1，使 σ 展幅回到 ℓ 的量级），应作为独立变更单独验证。

## 18. 140 局和棋深层机理审计、四大病灶定位与动态 c_scale + 四重防和棋铁壁落地

> 核心动因：在 Round 3 的 400 局 Arena 对决中，虽然候选模型斩获 162 胜 98 负成功换代，但和棋数依然高达 **140 局（35.0%）**。为什么模型在取得巨大局面优势甚至多子残局下依然频频成和？

### 18.1 140 局和棋全量归因审计（重大突破）

开发专用审计工具 `SSM/tools/audit_draw_attribution.py`，对全部 140 局和棋进行整局回溯与子力差轨迹分析，得出惊人结论：

- **A 方曾获大优/终局大优却成和（A 净错失胜势丢分项）**：**124 局（88.6%）**！
- **B 方（初代）大优被 A 顽强守和（A 防守成功得分项）**：11 局（7.9%）
- **势均力敌正常兑光和棋（理论均势）**：仅 5 局（3.5%）

**A 方大优成和的类型分布**：
1. **三次重复（Threefold Repetition）**：**73 局（58.9%）** —— 压倒性主要病灶！
2. **子力不足（Insufficient Material）**：**33 局（26.6%）** —— 优势方误将对方子力兑光至单轻子成和。
3. **逼和（Stalemate）**：**18 局（14.5%）** —— 单后/双车围困中无意识封死对方单王。

### 18.2 典型棋谱 Game 41（单后双车大优被逼平）根节点 MCTS 深度剖析

在 Game 41 中，黑方手握单后双车（净子力领先 +19 分），在第 70 步残局面对白单王：
- **盘面真相**：黑后在 e5，黑车在 h2。黑方手握一步绝杀着法 `e5f4#`（Qf4# 立即将死白王）；另一着法为 `h2f2+`（Rf2+ 习惯性晃步将军，该局面历史上已走过 1 次，走入即成二次重复）。
- **根因 1（c_scale 锁定导致 Q 增益上限封顶）**：
  在固定 $c_{\text{scale}} = 0.02$ 下，$\sigma(q̂) = (50 + \max N) \times 0.02 \times q̂$。在第一轮减半搜索时 $\max N=15$，最大 Q 贡献增益上限仅为 $(50+15) \times 0.02 = 1.30$！
  而神经网络由于在大量开局/中局人类对局中养成了“有将先叫将”的模式偏好，给习惯性将军步 `h2f2+` 的先验 logit 高达 **8.095**，给绝杀步 `e5f4#` 的 logit 仅为 **5.710**（logit 差距高达 **+2.385**）！
  即便绝杀步真值 $Q=1.0$，$1.30$ 的 Q 增益也根本无法翻盘 $+2.385$ 的先验差距！搜索被先验 Logit 彻底绑架！
- **根因 2（二次重复软惩罚无效）**：
  此前 `twofold_penalty = 0.15`，即便扣除，晃步局面残余估值仍有 $+0.85$，在超高先验压制下稳坐第一位。
- **根因 3（劣势方 2-ply 宣和前瞻盲区）**：
  三次重复往往并非优势方直接第 3 次走入，而是优势方走了一步非重复着，大劣方（单王）顺水推舟走入第 3 次重复宣和偷分。优势方在搜索前向中对此完全没有防范。

### 18.3 用户原创双轮动态 c_scale 调度机制

为彻底打破开局大局观与残局杀力纠偏的矛盾，落地用户原创的子力+步数双轮动态调度公式：

$$c_{\text{scale}}(\text{board}) = 0.07 \times \left(1 - \frac{\max(0, \text{mat}-4)}{78}\right) + 0.07 \times \left(\frac{\text{ply}+20}{128}\right)$$

- **区间截断**：严格 clip 在 $[0.015, 0.150]$。
- **动态特性**：
  - **开局满盘（mat=78, ply=0）**：$c_{\text{scale}} \approx 0.015$。压低 $\sigma$ 展幅，避免局部搜索噪声破坏价值网络的大局观与平衡性；
  - **残局决战（mat $\le 10$, ply $\ge 70$）**：$c_{\text{scale}}$ 自动激增至 **$0.10 \sim 0.14$**！
  - **纠偏威力**：在残局下，Q 增益上限从 $+1.3$ 瞬间放大到 **$+6.5 \sim +9.5$**，规则真值 $Q=1.0$ 的杀力信号可以直接碾碎任何高达 $+5.0$ 的先验偏差，将绝杀步瞬间送上榜首！
- **健壮性优化**：改用 python-chess 原生 `board.ply()`（自动处理 FEN 加载与合法推步），杜绝历史切片越界。

### 18.4 四重防和棋铁壁落地（Kit 搜索层）

在 `Kit/search/gumbel.py` 中落地四重铁壁：

1. **动态 $c_{\text{scale}}$ 调度机制**：在 `Gumbel.search` 与 `pi_prime` 导出中严格对齐当前盘面的动态尺度；
2. **大优方二次重复硬判负**：若优势方（$\text{net\_mat} \ge 2$）走入二次重复（`child_board.is_repetition(2)`），若开启 `twofold_penalty > 0`，直接置 `node.q = float(twofold_penalty)`（通常为 1.0），父节点视角的动作估值直接为 **$-1.0$**，在第一轮顺序减半中被全额淘汰；
3. **劣势方 2-ply 宣和前瞻截断**：若优势方走完一步后，对方在下回合具有合法宣和权（`child_board.can_claim_threefold_repetition()` 为 True），由于大劣方必宣和，优势方直接将其视为终端和棋并施加重罚截断（免除无效前向计算并彻底封死偷和可能）；
4. **逼和与子力不足门限统一调整**：逼和与子力不足的判定门限统一下调为 $\text{net\_mat} \ge 1$ 兵，杜绝单兵升变轻子和棋或送吃和棋。

### 18.5 全量边界单测验证与实战死活复算

在 `Kit/tests/test_penalties.py` 扩充 9 大完整边界单测套件：
- `test_default_penalties_zero`：默认配置保持纯规则真值；
- `test_stalemate_penalty_when_ahead`：优势方逼和判负，避开逼和选绝杀；
- `test_stalemate_no_penalty_when_behind`：劣势方逼和自救不予惩罚；
